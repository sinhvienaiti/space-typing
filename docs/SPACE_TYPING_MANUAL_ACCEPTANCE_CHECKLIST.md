# Space Typing Manual Acceptance Checklist

Updated: 2026-10-12

## Purpose

This file is the canonical backlog for manual/product checks that automation cannot honestly replace.

Manual acceptance is **deferred and non-blocking by default** so implementation work can continue without waiting for owner testing after every technical checkpoint.

A pending manual item becomes a blocker only when one of these conditions is true:

1. a merge/release decision depends on that acceptance;
2. the next task directly changes the same subsystem and would make the pending result ambiguous or obsolete;
3. the roadmap explicitly requires the result as an input to a destructive/irreversible integration step.

Otherwise, keep the item `PENDING`, continue independent work, and return to this checklist before final integration/release.

## Status values

- `PENDING` — not manually tested yet; does not block unrelated work.
- `PASS` — manually accepted on the recorded commit/environment.
- `FAIL` — issue reproduced; create/fix a focused defect, rerun automated checks, then retest this item.
- `STALE` — previously tested, but later changes touched the same subsystem and require retest.
- `N/A` — not applicable to the tested target/environment, with a reason recorded.

## Execution policy

- Do not stop unrelated implementation merely because an item below is `PENDING`.
- Do not mark an item `PASS` from CI, screenshots generated by automation, static code inspection, or assumptions.
- Record the exact tested commit SHA and environment for every `PASS` or `FAIL`.
- If a later commit changes the same subsystem, change the relevant prior `PASS` to `STALE`.
- A failed item should produce a narrowly scoped fix; do not reopen already-complete unrelated milestones.
- Before final merge/release, resolve all release-required `PENDING`, `FAIL`, and `STALE` items.

# Failure workflow

When any item fails, record the defect using this format:

```text
Manual item: P2.x / P7.x
Tested SHA:
Environment:
Expected:
Actual:
Reproduction steps:
Screenshot/video/audio:
Affected subsystem:
Severity: blocker / major / minor / polish
```

Then:

1. fix only the affected subsystem;
2. run focused automated tests/audits;
3. run required full CI for the integration checkpoint;
4. retest the failed manual item;
5. mark related manual items `STALE` only if the fix could affect them.

# Release rule

Implementation may continue with manual items pending, but **final merge/release acceptance must not claim these checks passed until the owner actually performs them on the recorded candidate SHA/environment**.

At the end of the implementation roadmap, explicitly remind the owner to open this file and complete all remaining release-required manual checks.
